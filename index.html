WHAT WE INSPECT

무엇을 검사하는가

버튼이 있는지 보는 게 아닙니다.
업무가 끝까지 되는지, 데이터가 맞는지, 남의 정보가 보이는지 확인합니다.

01약속한 기능이 구현됐는가

계약·요구사항을 테스트 항목과 연결합니다. '고객 등록 → 업무 처리 → 저장 → 재조회'처럼 실제 업무 흐름을 끝까지 실행합니다. 필수값 누락·경계값·중복 클릭·취소와 재시도도 확인합니다.

02데이터가 정확히 이어지는가

화면 입력값·API 응답·DB 저장값·조회와 집계·다운로드를 대조합니다. 금액 변경 후 상세 화면·합계·내보내기가 일치하는지 확인합니다.

03남의 정보에 접근할 수 없는가

역할별 테스트 계정으로 읽기·수정·삭제 권한을 검사합니다. 다른 레코드 ID를 요청했을 때 서버가 권한을 검사하는지 확인합니다. 메뉴를 숨긴 것만으로 됐다고 판정하지 않습니다.

04실제 환경에서 쓸 수 있는가

합의한 모바일·데스크톱·브라우저·OS 조합에서 테스트합니다. 느린 연결과 실패 후 복구, 파일 업로드, 뒤로 가기까지 확인합니다.

05장애를 파악하고 복구할 수 있는가

오류 응답과 로그·환경설정·외부 의존성·백업과 복구 절차를 확인합니다. 성능은 측정 조건과 허용 응답시간을 먼저 정한 뒤 측정합니다.

06회사가 납품물을 통제할 수 있는가

저장소·호스팅·도메인·DB의 소유 주체와 관리자 권한을 확인합니다. 문서만 보고 제3자가 빌드·재배포·복구할 수 있는지 직접 재현합니다.

HOW WE WORK

어떻게 수행하는가

눌러서 펼치면 각 단계의 실행 내용이 보입니다.

STEP 1

착수 합의

+
대상 버전·핵심 업무·테스트 계정·환경·데이터·제외 범위·종료 조건을 고정합니다. 실제 결제·메일 발송·삭제처럼 영향을 주는 동작은 시험 환경과 허용 범위를 먼저 정합니다.
원칙: 합의되지 않은 범위는 손대지 않습니다.
STEP 2

테스트 설계 및 실행

+
각 요구사항에 테스트 ID를 부여하고 사전조건·입력·절차·기대 결과를 작성합니다. 실행 후 실제 결과와 화면·로그·응답을 같은 ID에 연결합니다.
원칙: 접근 권한이나 환경 때문에 실행하지 못한 항목은 통과로 처리하지 않습니다.
STEP 3

재현 가능한 수정 요청 전달

+
결함마다 발생 환경·재현 순서·기대와 실제 결과·증거·업무 영향·심각도와 수정 우선순위를 기록합니다. '작동이 이상하다'가 아니라 개발사가 같은 문제를 다시 발생시킬 수 있는 수준으로 전달합니다.
STEP 4

수정본 재검증

+
수정된 버전에서 원래 실패한 테스트를 다시 실행하고, 변경의 영향을 받는 주변 기능도 회귀시험합니다.
원칙: 개발사의 '수정 완료'와 검수자의 '해결 확인'은 다릅니다.
STEP 5

인수 판단 보고

+
회사 오너에게는 인수 가능 범위와 미해결 위험을 짧게, 개발사에게는 상세 결함·재검증 기록을 제공합니다.
원칙: 최종 인수 결정은 고객이 합니다. 검수자는 판단 근거와 권고를 제공합니다.

FIX
핵심 미해결 P1 — 조건부 인수. 소유권·보안의 문제는 고치기 전엔 안 넘어감.
PASS
P2·P3만 존재 — 인수 가능. 관찰사항으로 명시.
PASS 금지
핵심 기준 UNKNOWN — 확인 못한 항목이 있으면 PASS를 줄 수 없음.
“UNKNOWN은 정보 표시가 아니다.
핵심 통제항목이 UNKNOWN이면 사실상 검증 실패다.”
